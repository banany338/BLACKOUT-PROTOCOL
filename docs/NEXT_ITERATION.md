# Review-driven direction: make the recovery finding the product

Updated 2026-10-04: the private organisation workspace, direct editing, local encrypted storage, provider-export import, own-map team checks and portable build are now implemented. Browser checks pass; real-team comprehension and delivery/field checks remain. Use `PROGRESS.md` for current status and the remaining acceptance work. The priorities below preserve the rationale.

## Assessment

The outside reviews identify real adoption and demonstration gaps. A score based on repository prose and no observed demo is not a measured jury outcome. Their strongest point is that the fictional exercise is easier to demonstrate than the product's immediate value for an unfamiliar organisation.

## Priority 1 — Prove the existing complete journey

Close the browser/device checks in `VALIDATION.md`. Capture the baseline finding, a three-role verification decision, the improved route and the actual offline export. Record failures and fixes. Add screenshots to the README and rehearse the three-minute demo. Do not label loopback transport tests as physical LAN validation.

## Priority 2 — A useful first result from the user's own arrangements

Make the entry choice explicit: try the example, or describe your organisation. A short guided form should capture the primary identity, recovery email, phone, location/access dependencies of recovery materials, and responsible person. Preserve evidence as user-reported or unknown until confirmed. Never ask for passwords, recovery codes or mailbox contents.

Acceptance: someone can replace Harbor Aid with their own declared arrangements, understand a blocked recovery route, and leave with an owned action without hosting a multiplayer session. Fixture-specific assumptions and policies must not silently carry into that real organisation's model.

## Priority 3 — Put the recovery result at the centre

Lead with: “If this account or phone is lost, which activities stop, and what independent route remains?” Show the prerequisite that blocks recovery and evaluate small candidate changes using the same engine. Compare the same failure and targets, and list every added assumption. A ranked single-failure sweep is useful only after its failure semantics and explanations are tested.

Acceptance: a judge sees the weakness, cause and justified improvement in under a minute. No generic security score or unsupported recovery guarantee.

## Priority 4 — Remove setup from the first-use journey

Offer a direct demonstration route and a clear supported delivery choice: a packaged local application or an appropriately secured hosted deployment. Keep the local planner useful without requiring team-room setup. Package/deployment work must include its actual authentication, TLS, retention and update requirements; changing the README is insufficient.

Do not claim a physical offline application merely because its assets are local. Distinguish the standalone exported reference, a running local-server session, and any future installable application.

## Priority 5 — One narrow integration, if it changes a decision

Consider an import of a documented provider export or a read-only admin API only when the necessary fields are available and the team has an authorised test environment. Show source, retrieval time, missing fields and owner confirmation. API-discovered recovery contact fields alone do not establish that the person can access the destination or complete a recovery procedure.

An integration is valuable if it replaces uncertain manual work and is tested. A fake connector, an unused AI API or live destructive account actions would weaken the demonstration.

## Lower priority

Dark mode, extra illustrations, stochastic adversaries, novel graph algorithms, larger untested capacity, and a second narrative scenario. None should displace the complete validated product loop.

## Submission positioning

“Find and fix recovery dead ends before a critical account disappears.”

Present the map and actionable finding first; use the cooperative rehearsal to test the team's response. Show implementation evidence and describe prototype limits precisely. Do not invent guarantees, user-study results, provenance concerns, or competition scores.
